Optional feature modules¶

Status: setup management and songs/setlists use the static module menu. Panic, the MIDI cable tester and MIDI Interface use the right-hand page cycle. Firmware-specific modules are registered by their target. The broader organization below remains guidance for subsequent features.

Purpose¶

Organize features such as a MIDI monitor, MIDI cable tester and MIDI processor as small optional modules around a shared core. Each module should work without the others. Modules do not call one another directly.

Ownership and dependencies¶

Each module owns its configuration, private state, pages, commands, button actions, processing logic and tests.

The core owns physical MIDI ports, input decoding, output scheduling, buttons, displays, storage and time. Modules access these through small interfaces rather than accessing hardware directly. Hardware-specific implementations stay in the existing maker directories.

firmware/include/cntrl/midi_outputs.h defines the enabled physical MIDI output connections in cntrl::midi::output_connections: currently DIN and TRS. Each connection carries its configuration name, display label and bridge route. USB outputs are listed separately. Routing, Panic, the cable tester and MIDI-interface output indicators use this shared metadata. Input ports remain independent. Omniports are not enabled by this extraction; their MIDI configuration, target driver support and presentation of additional ports remain later work.

Dependencies point from modules to shared core interfaces. The core coordinates modules through an explicit registry; it does not depend on individual modules' implementation details. Share functionality only when real modules need it.

MIDI roles¶

Role Example Behavior
Observer MIDI monitor Receives events without consuming or changing them
Processor Filter, remapper, arpeggiator Receives events on an explicitly configured route and produces output
Active tool MIDI cable tester Temporarily claims selected ports and runs a test

These roles describe participation, rather than requiring every module to implement the same set of methods.

Enabling a monitor must not change routing. A processor must not automatically receive everything another processor emits. A cable tester must not inject test messages into live performance routes.

Routing and resource ownership¶

The core determines which events reach each module, where generated messages go, and whether ports are available. Processing chains are explicit routes, not implicit consequences of module registration order.

A monitor can observe configured points before or after processing. Observation does not consume an event or prevent its normal delivery.

An active tool explicitly claims the ports needed for its operation and releases them when finished or deactivated. The core coordinates access so test traffic does not interfere with performance traffic. Conflicting use must be resolved before the operation starts.

Installed and enabled¶

Keep build inclusion separate from setup activation:

  • Installed: the firmware build includes the module. Excluded modules contribute no code or assets.
  • Enabled: the setup selects an installed module. Disabled modules perform no work.

Start with static linking and an explicit module registry. Runtime plugin loading, automatic discovery and a general dependency framework are unnecessary.

Lifecycle and execution¶

A module exposes only the operations it needs: initialization, activation and deactivation, event handling, and advancement of scheduled work where applicable. Private state belongs to the module; shared hardware state belongs to the core.

Execution is cooperative and bounded. A busy monitor or processor must not stall MIDI delivery or the UI. Scheduled processing uses core-provided time and output scheduling rather than blocking waits.

Establishing the interfaces¶

The cable tester, MIDI interface and Panic use target adapters for physical services while owning their own behavior; the right-page renderer supplies their shared display style. A future MIDI monitor should reuse those services. Establish additional shared interfaces only when another module actually needs them.

Verify each module's logic independently. Also verify that observers leave routing unchanged, processors follow configured routes, active tools respect port ownership, and deactivation releases resources. Hardware behavior requires separate physical verification.

Additional work beyond the prompt¶

None. Current modules are documented in midi-cable-test.md, midi-interface.md and panic.md.
