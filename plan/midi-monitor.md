# MIDI monitor page

Implemented in the shared runtime, sink and page system. The user guide is
[MIDI monitor](../doc/midi-monitor.md). Automated verification covers the
behavior below; physical timing and display qualification remain outstanding.

## Outcome and scope

Add a named `midi-monitor` utility page occupying one, two or three windows.
The layout follows the configured window count:

| Windows | Layout, left to right |
| --- | --- |
| 1 | Combined incoming and outgoing traffic in chronological order |
| 2 | Incoming, Outgoing |
| 3 | Incoming, Combined, Outgoing |

Every layout covers all enabled MIDI endpoints exposed by the target,
including DIN, TRS, USB device cables and USB host endpoints. Combined rows
include an explicit Incoming or Outgoing marker.

Observe received traffic before routing, filtering or processing. Observe
outgoing traffic after a successful local transport write. Include forwarded
messages and messages generated by patches, counters, expression controls,
clocks, MIDI files, routing processors, panic and cleanup. Include diagnostic
traffic while a cable test is active, with its diagnostic origin identified.

The following sections record the implemented design and its acceptance criteria.

## Page configuration and placement

```toml
[pages.monitor]
type = 'midi-monitor'
windows = 2
```

- Default this page type to two windows. Accept explicit counts of 1, 2 or 3,
  rejecting zero, larger counts and requests exceeding the target's displays.
  A single-display target requires an explicit `windows = 1`.
- Follow the existing utility-page allocation: take the requested number of
  rightmost physical displays. Leave the active patch-switcher in any remaining
  displays according to its existing allocation rules. A three-window monitor
  on a three-display target occupies all displays while patch execution continues.
- Give each window its layout-specific heading. Do not use the existing utility
  rendering behavior that repeats one heading and distributes generic body rows.
- Use the existing Pages and tools menu, page cycling and Back behavior.
  Do not add the monitor to every setup automatically.
- Opening or closing the page must not start, stop or reconfigure forwarding,
  routes, recording, playback, clocks or USB connections. A disabled transport
  cannot supply traffic that its adapter does not read.

Extend the current page models, type mappings, layout compilation, document
validation and export. Preserve the meaning of existing page identifiers and
keep internal confirmation screens separate from configurable page types.

## Observation points and meaning

Use the shared runtime and output sink, with hardware reads and writes remaining
in target adapters. Audit every physical output path for bypasses before adding
the observer.

1. **Incoming:** tap events immediately after `midi_read_event` succeeds, before
   the runtime's USB-enabled check, recording, clock detection, exclusive tool
   handling, routing and legacy forwarding. Incoming messages remain visible
   when forwarding is off or a processing rule drops them.
2. **Outgoing:** tap the successful-write path in `midi::Sink::submit`. A failed
   or blocked write creates no outgoing traffic entry. Retrying a blocked write
   must not create duplicate entries. Any adapter path that bypasses this sink
   must use the same observation contract without counting a write twice.
3. **Internal processing:** do not count internal route-to-route handoffs as
   additional input or output traffic. A fan-out produces one outgoing entry
   per destination, using the transformed bytes actually written there.

“Outgoing” means accepted by the local transport driver. It does not prove
arrival at a receiver or acknowledgement by an instrument. Do not label queued
patch messages as sent. Monitoring itself must never transmit MIDI.

## Event representation and presentation

Each entry records a monotonic timestamp, observation sequence, direction,
endpoint identity and observed bytes. Use the existing endpoint registry and
saved aliases for labels. Direction is relative to the pedal. Use one timestamp
origin for all windows and handle the hardware timer rolling over.

Show compact rows containing time, endpoint and a decoded message summary.
Show channels as 1–16 and programs as 1–128, matching existing authoring and
display conventions. Include hexadecimal bytes alongside the summary so
the monitor can distinguish literal Note Off from zero-velocity Note On.

Cover every MIDI message category: channel voice messages, system common,
real-time and SysEx. In particular, do not silently omit Clock, Active Sensing,
Start, Continue, Stop, Reset, or messages on channels other than channel 1.

Use independent input decoder state per endpoint so running status and
interleaved streams cannot corrupt each other. Reuse the existing MIDI parser
and message definitions where their behavior fits. Real-time bytes interleaved
with SysEx remain independently visible. Mark incomplete or malformed input as
raw or incomplete traffic instead of fabricating a complete MIDI message.

Represent SysEx as ordered bounded chunks with start, continuation and end
indicators. Show payload length and a bounded byte preview. Clearly mark bytes
omitted from a preview; do not imply that the full payload is retained. USB
padding and packet headers are transport framing, not additional MIDI bytes.

## Controls and history

Use the existing logical control roles and target-specific button labels.
Controls are:

- Confirm freezes the current view; Confirm again returns to live traffic.
- Previous and Next move through retained history while frozen.
- Back uses the normal utility-page navigation.

Use one chronological history with combined and direction-specific views.
A shared history cursor keeps all windows at the same observation point while
browsing. Each window shows the most recent matching rows up to that cursor.
The Combined window interleaves both directions using observation sequence
to break timestamp ties. In the three-window layout, it reuses the same entries
shown in the directional windows without capturing or counting them again.
Show `No traffic`, `No input` or `No output` as appropriate to the view.

Start capture with empty history when entering the page and stop it on leaving.
Freeze stops scrolling, not MIDI processing or capture. If new traffic replaces
the frozen position, show that the retained history has advanced and clamp the
cursor to the oldest available entry. A setup change closes the monitor and
clears its decoder state and history. A disconnect marks the endpoint change
and resets that endpoint's partial decoder state; it must not complete a message
using bytes from a replacement device.

## Responsiveness and overload

All MIDI categories are eligible for observation, but a finite screen and
bounded RAM cannot provide a lossless archive at arbitrary traffic rates.
Make that limitation visible rather than silently filtering busy traffic.

- Use 128 history entries and at most three MIDI bytes per entry. Capture and
  decoder storage together remain below 16 KiB and use the existing heap budget
  while the page is open. Do not allocate per received byte or grow with SysEx length.
- Capture only bounded binary data in MIDI service paths. Decode and format
  text outside those paths, with bounded work per UI update.
- Overwrite the oldest monitor entries when full. Report cumulative overwritten
  entries separately from actual MIDI drop or failure counters. Three-byte SysEx
  chunks retain all their bytes, so there are no truncated payload previews.
- Bound display refresh frequency independently of event arrival. Clock and
  other dense traffic must not force one screen redraw per event.
- Keep capture nonblocking. Display congestion or monitor overflow must never
  backpressure MIDI, delay clock service, retain borrowed output buffers, or
  consume the MIDI recorder's queue.

No SD logging, host streaming, filters or persistent monitor preferences are
included. Those would be separate features.

## Implementation

The bounded observer connects before input processing and after successful sink
writes. It is inactive while the page is closed. The page type round-trips
through compilation and export, with firmware validation of all three window
counts. Shared views implement freezing, browsing, overflow indicators and
lifecycle handling. Native tests cover capture, routing, output acceptance,
decoding, controls and rendering; Python tests cover configuration and export.

Relevant owning paths are `cntrl/patch_switcher/models.py`,
`cntrl/patch_switcher/layout.py`, `firmware/include/cntrl/document.h`,
`firmware/include/cntrl/midi_runtime.h`,
`firmware/include/cntrl/midi_bridge.h`, and the shared
`firmware/include/cntrl/ui/` page and presentation code. Reuse the existing
compiler/export, page-layout and native MIDI test suites.

## Acceptance and verification

- Configuration round-trips through compilation and export for window counts
  1, 2 and 3. Invalid counts and requests exceeding the target's displays fail
  validation. Verify explicit single-window configuration on a one-display target.
- Verify each layout's headings, direction markers and chronological ordering.
  Three-window views share history and never double-count observations.
- On a three-display target, one- and two-window monitors leave the remaining
  performance displays operating. A three-window monitor occupies all displays
  while background patch execution continues.
- Fixtures exercise every MIDI category, running status, zero-velocity Note On,
  multiple channels, multiple endpoints, split SysEx, real-time interleaving,
  malformed input and timer rollover.
- Received messages dropped by routing appear only in Incoming. Transformed
  and generated traffic appears in Outgoing with its actual destination and
  bytes. Fan-out, cleanup, panic and diagnostic writes are counted once per
  successful destination write.
- Blocked, failed and retried output writes never appear as successful traffic
  until accepted. Monitor history overflow does not change MIDI delivery.
- Freeze, history browsing, page changes, setup changes and disconnects follow
  the stated lifecycle without modifying musical state.
- Sustained Clock and long SysEx keep storage and rendering work bounded.
  Measure scan gaps and MIDI service time with monitoring open and closed.
  Physically qualify simultaneous DIN/TRS and USB traffic on the supported
  hardware. Automated tests alone do not establish wire timing or display
  responsiveness.

## Remaining physical qualification

Measure MIDI service time and scan gaps with the monitor open and closed under
simultaneous traffic, and check the readability and refresh rate on the actual
displays for all three layouts. Verify disconnect and replacement behavior on
the enabled physical transports. Record target-specific evidence in the
target's existing directory. No firmware deployment or live hardware test is
implied by the automated checks.
