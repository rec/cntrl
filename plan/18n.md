# Runtime UI internationalization

## Goal

Let the user install several UI languages and switch between them on the pedal
without restarting it, reloading the setup or interrupting MIDI. Longer captions
and different scripts must remain readable on every supported display geometry.

The feature covers firmware-owned menus, prompts, page captions, settings,
confirmation dialogs, status words and user-facing errors. Patch, instrument,
setup and file names remain exactly as authored. MIDI bytes, configuration keys,
USB command names and machine-readable diagnostics keep their existing meaning.
Translate the UI explanation of an error, retaining its stable diagnostic code.

This is a plan, not authorization to implement it or change dependencies.

## Existing code to build on

- `firmware/include/cntrl/module_menu.h`, `ui/prompts.h`, `ui/pages.h` and
  `ui/page_host.h` contain firmware-owned English captions. The inventory must
  also cover other dialogs, feature modules and target-supplied menu names.
- `doc/formatting.md` already specifies automatic fitting: choose the largest
  available bitmap size that fits the field's width and height. Some related
  lines share a size. There are no authored `font_size` controls.
- `cntrl/fonts/ui.py` currently prepares printable ASCII for built-in UI faces.
  `cntrl/fonts/outline.py` already uses host-side shaping and bidi support, and
  `cntrl/fonts/assets.py` prepares sparse Unicode text runs for setup text.
  Unicode setup text therefore does not establish Unicode support for all UI.
- `firmware/include/cntrl/ui/fonts.h` and `ui/font_assets.h` render prepared
  bitmap assets. Extend these paths rather than adding another text renderer.
- `TextLine.text` and the prompt builder have 64-byte buffers. A translated
  caption may need more UTF-8 bytes even when it occupies fewer screen pixels.
- Device-global settings, source snapshots, backup and emulator support already
  exist. Language selection must participate in those workflows.

Shared localization code belongs in the generic firmware and host packages.
Target-specific font selections, resources and measurements stay with the target.

## Language catalogues

Use tracked UTF-8 TOML catalogues with stable message IDs, not English sentences
as lookup keys. English is the complete reference catalogue. Translation entries
include context for the translator, typed placeholders and, where useful, an
approved shorter caption. For example:

```toml
language = 'de'
name = 'Deutsch'
direction = 'ltr'

[messages.pages_and_tools]
text = 'Seiten und Werkzeuge'
short = 'Seiten / Tools'

[messages.storage_free]
text = '{amount} frei'
```

Keep placeholder definitions and UI role constraints in the reference catalogue
or its associated schema. A translation cannot introduce a placeholder, remove
a required value, change a value's type or supply a printf format string.
Resolve messages by semantic ID throughout the UI, including captions supplied
by feature modules. Do not translate raw strings opportunistically at paint time.

Replace concatenated English prose with complete templates so translations can
reorder values. Where the existing UI needs counts, support the selected
language's required plural forms and compile their selection rules on the host.
Do not add a general locale database to the firmware. Preserve established MIDI
notation, note names, units and filenames unless a particular display field has
an explicitly translated presentation.

Physical switch labels remain hardware labels. Translate their actions and the
complete surrounding prompt, allowing label placement to differ by language.
Do not assume every translated prompt has the English label/action order.

## Assets and installation

Prepare language packs on the host using the existing font shaping and bitmap
pipeline. Ship ready-made packs with releases so ordinary users do not need a
compiler, font tools or a firmware variant to select a language.

A versioned pack contains the locale tag, native display name, supported text
direction, message-ID table, templates, short forms, layout/font roles and the
required bitmap glyphs and prepared runs. Validate its version, lengths,
checksum, placeholders, glyph coverage and target display/font requirements
before activation. Identify locales by stable tags such as `en` or `de`, never
by their position in the installed-language menu.

Keep complete packs on SD and retain only the active language's required indexes
and bounded font/run working set in RAM. Keep a minimal English recovery UI in
flash so missing SD assets cannot make the pedal unusable. Reuse existing asset
transfer, integrity checking and deployment mechanisms. Catalogue additions must
not require rebuilding the MIDI engine.

The translation's glyph set determines the font subset. Do not embed every
Unicode glyph or every language in RAM or instruction RAM. Preserve authored
setup font assets and their ownership when replacing the UI language's assets.

## Caption length and font sizes

Fit the localized result against the actual allocated field, after padding,
icons, switch labels and dynamic values have been accounted for. Use measured
glyph bounds and advances, not character counts or the English caption's size.
Recompute when the language, value, page allocation or display geometry changes.

Use this order for each UI role:

1. Try the full caption at the largest available size that fits.
2. Use the page's existing wrapping or multi-line layout where that role permits
   it. Prepare and measure the wrapped runs correctly for the language.
3. If the full caption cannot fit above the role's readable minimum, try its
   translator-supplied short form, again choosing the largest fitting size.
4. Apply the role's explicit overflow rule if neither fits. Ordinary labels may
   use an ellipsis; safety confirmations must retain their action and consequence
   and use an expanded dialog or additional screen instead of losing meaning.

Available sizes, minimum readable height, line count and emphasis are UI-role
and target constraints. A locale may select a suitable font family and prepared
size range, especially for scripts needing larger characters or different line
metrics. Do not introduce per-setup manual font sizes for translated UI labels.
Preserve proportions rather than squeezing or stretching translated glyphs.

Include ascenders, descenders, diacritics and script-specific extents in vertical
fitting. Existing groups of equal-sized lines should still share the smallest
fitting size required by the group. Avoid changing page allocations or moving
switch actions merely because one language is longer.

Live numeric fields should reserve space for their supported range, or use a
small stable set of fitting sizes, to avoid visible size oscillation while the
value changes. Do not reserve for every possible string on every page globally.
Use the same rules with zero, one or two frame buffers and with animations off;
scrolling cannot be required to read a caption.

The pack builder must report captions which cannot meet the role's minimum size
on a supported geometry. A translation is not qualified just because tiny text
technically fits. Review short forms for meaning, not only their pixel width.

## Unicode, shaping and dynamic content

Use UTF-8 with byte capacities distinct from visual width. Audit fixed buffers
and formatting calls before substituting translated strings. Define bounded
template output capacities from actual UI needs, reject oversized pack entries
and never cut a UTF-8 sequence or a displayed grapheme when shortening text.
Do not enlarge every `Pane` field to the largest possible catalogue entry.
Keep long static runs in the pack where the renderer can reference them safely.

Reuse host shaping for static captions, short forms and approved line breaks.
Prepare dynamic templates as ordered text/value spans with validated boundaries,
font coverage and bidi isolation for inserted names and numbers. Arbitrarily
concatenating pre-shaped fragments is insufficient for contextual shaping.

Before qualifying a joining or right-to-left script, demonstrate correct mixed
text, placeholders, line wrapping and punctuation. Use complete prepared runs for
finite forms and separately laid-out value fields where this avoids runtime
shaping. If required free-form prose cannot be rendered correctly that way,
identify the necessary bounded runtime shaping work and obtain agreement before
adding it. Do not advertise support based only on displaying isolated glyphs.

Text direction affects text alignment and reading order. It must not silently
reverse the pedal's physical window order, region allocation, switch assignments
or navigation semantics. Any mirroring of those controls needs a separate design
decision and tests.

Incoming text banners currently have an ASCII transport contract. Localize
their surrounding warning/cue captions, but preserve the sender's payload.
Changing USB or SysEx text encoding is separate work and is not part of this
plan. Likewise, switching language does not translate authored names or make
arbitrary new input glyphs available automatically.

## Runtime selection and persistence

Add a Language entry to the existing Pages and tools menu. List installed
languages by native names, with the current selection marked. Include those
native names in the language-picker assets so they remain readable even before
their language is active. Keep the English recovery choice accessible.

Prepare a candidate catalogue and its required font resources cooperatively,
using bounded work between MIDI servicing. Check peak allocation while the old
language is still usable. Once preparation succeeds, persist and publish the
selection, invalidate cached translated views and repaint the visible UI.
Release superseded UI assets when no render operation still references them.

On missing assets, invalid packs, insufficient memory or persistence failure,
retain the current language and show a usable error. At boot, a missing selected
pack falls back to the embedded English recovery UI without destroying the
stored preference or rewriting setups. Switching must preserve held notes,
loop playback/recording, tap tempo, page focus and pending patch actions. It must
not invoke the setup reload path or allocate a frame buffer.

Use the existing device-global preference service for persistence and host
set/clear/read commands. A locale tag is a string, whereas the current registry
and journal contain fixed numeric fields. Design a versioned extension with
explicit old-record handling, rather than storing a menu index or silently
reinterpreting a numeric setting. Update semantic overlay snapshots, backups,
recovery, sync and emulator bootstrap together; do not create an independent
language-preference store with different restore behavior.

The exact relationship between a setup's compiled language default and the live
device preference is an implementation decision listed below. Whatever policy
is selected must let the on-pedal Language command change the current UI
immediately and report its scope clearly.

## Implementation sequence

1. Inventory visible literals and their UI roles, dynamic values and overflow
   behavior. Distinguish user-facing explanations from protocol identifiers.
2. Introduce reference message IDs and typed catalogue validation. Convert the
   whole built-in English UI, including target module menus, without changing
   its controls or behavior. Remove replaced literal paths completely.
3. Extend the existing font/run pipeline for catalogue glyph coverage, role
   metrics and translated fitting. Audit buffers, render-cache keys, wrapping
   and prepared-run lifetimes.
4. Add pack installation and transactional runtime selection through the existing
   menu and preference service, including the journal/overlay format change.
5. Add reviewed translations and native language names. Proposed initial
   qualification is English, French and German, plus an intentionally expanded
   test catalogue. Broader script support requires the qualification above.
6. Integrate packs and selected locale with release packaging, downloads,
   backup/restore, source recovery and the emulator. Run the memory and timing
   checks before enabling the feature in a release.

## Verification and acceptance

- Catalogue tests reject missing required messages, invalid placeholders,
  unsupported forms, absent glyphs and corrupt/incompatible packs. Incomplete
  development catalogues may use explicit English fallback; release validation
  must report untranslated entries rather than hide them.
- Renderer regression images cover short and expanded captions, accents and
  combining marks, longest supported dynamic values, short forms, wrapping,
  grouped sizes and ellipsis at the readable minimum. Check every supported
  window allocation and the smallest target display geometry.
- Test correct shaping, bidi and safe shortening before enabling each additional
  script. Include mixed numbers and authored names, not just static greetings.
- Runtime tests switch language with held notes, recording, playback and active
  navigation. Assert unchanged MIDI output/timing and preserved performance
  state. Exercise failed reads, memory exhaustion, removed SD assets and restart.
- Verify selected-locale restoration, clear behavior, missing-pack fallback,
  device-global overlay recovery and emulator parity. Test old preference
  records and current records explicitly across the format change.
- Measure executable flash, ITCM, static RAM1/RAM2, active catalogue/font RAM,
  peak switching RAM, pack sizes and worst-case cooperative work duration.
  Retain existing memory-budget reserves and time-critical MIDI placement.
- Review emulator screenshots and physical-display readability with speakers of
  each released language. Automated pixel fitting does not establish usability.

Acceptance requires a usable, complete localized UI, runtime switching without
performance interruption, no unreadably small required captions and recoverable
behavior when optional language assets are unavailable.

## Decisions before implementation

- Confirm initial languages and whether right-to-left or joining scripts are
  required in the first release. English/French/German exercises expansion and
  accents but does not qualify those scripts.
- Choose preference scope. Recommended: a device-wide language selection that
  remains in force across setup changes, with a compiled default when unset.
  If setup-level language overrides are wanted, define how the runtime picker
  sets or clears that local override without appearing to ignore the user.
- Agree readable minimums and overflow behavior for each UI role on actual
  displays. Start from the current target's usable sizes and review them rather
  than applying an arbitrary percentage reduction to every translation.
